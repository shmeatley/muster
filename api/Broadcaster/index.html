Broadcaster

Cross-server delivery of finalized matches.

MemoryStore is the ledger; MessagingService is the doorbell. A match is written and flipped to Ready before any message is published, so the message only ever says "go look" sooner than polling would have. Drop every message and the system still works — it just gets slower, and it notices.

Addressing

One topic per server, <namespace><version>:<serverId>, and each instance subscribes to exactly one. A match publishes only to the distinct servers holding its members, which is typically two to six.

The alternative — one shared topic every server filters — looks simpler and scales far worse. Roblox's per-universe receive budget is 400 + 200 x servers per minute, and a shared topic spends servers of that on every single match, which pins the whole experience at roughly 200 matches per minute no matter how large it grows. Per-server topics spend a handful per match regardless of fleet size.

Payload

Small envelopes ride along inside the message, saving the receiver a read. Larger ones send just the matchId and the receiver fetches from the ledger. Either way the message is advisory, so an envelope that arrives inline is safe to trust: it only exists because the commit already succeeded.

Health

If a publish fails, or a match is discovered by polling that a doorbell should have announced, the broadcaster marks itself unhealthy for a while. Tickets react by tightening their poll cap, so a MessagingService outage costs seconds of extra latency instead of minutes — and costs nothing at all while things are working.
