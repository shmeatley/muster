QuickPlay

Backfilling players into matches that are already running.

Muster's ordinary path only ever forms new matches. Quick Play adds the other one: a live match server advertises itself, and a queued player who fits drops straight into it instead of waiting for a fresh lobby to fill.

It is off unless a queue asks for it, since it is a casual-mode feature:

local casual = Muster.new({ name = "casual", size = 8, quickPlay = true })

Quick Play ignores rating entirely. There is no window, no relaxation and no banding; a listing with a free seat takes the next player who wants it. Do not turn it on for a ranked queue.

On the match server

local listing = Muster.Result.unwrap(casual.quickplay:host({
	data = { accessCode = code, placeId = ARENA_PLACE },
}))

listing:setOpen(false)  -- round underway; stop taking players
listing:close()         -- delist immediately

The handle is kept up to date by the queue's own worker pass, so a match server needs one Muster.new and one host call. Its player count refreshes every heartbeatInterval (30 s), and a server that dies is delisted by listingExpiration (90 s) without anybody cleaning up.

In the lobby

casual.quickPlayMatched:connect(function(assignment)
	TeleportService:TeleportToPrivateServer(
		assignment.data.placeId, assignment.data.accessCode, players)
end)

casual:quickPlay(player.UserId)

Matchmaker:quickPlay writes an ordinary ticket flagged for backfill and then looks for a seat immediately. If every listed match is full the player just stays in the normal queue and forms a fresh match the usual way, retrying the search every searchInterval while they wait. There is no separate queue and no dead end: the two paths race, and whichever resolves first wins.

Taking the last seat

Every claim is a compare-and-set on the listing record, so when fifty lobby servers see the same 7/8 match, exactly one of them gets the seat and the rest move on to their next candidate. Claimed seats are held as reservations until the players arrive, which is what stops two lobbies from both filling a slot inside one heartbeat window. See Listings.

Lanes

A MemoryStore range read returns at most 200 items, so listings shard into lanes exactly as tickets do, by hash, with the layout stamped into every key. The count starts at one and doubles once a lane is consistently too full to read in one go, so a game with six live matches pays for none of it. Pin it with quickPlay.lanes if you would rather.

Functions​

host​

</>
QuickPlay.host(
self: any,
options: HostOptions
) → Result<HostedListing>

Advertises this server as joinable.

Call it once the match server is ready to take players, with whatever a joining server needs to reach you: 

queue.quickplay:host({ data = { accessCode = code, placeId = ARENA_PLACE } })

data is delivered verbatim as assignment.data and must survive a JSON round trip, within quickPlay.maxListingDataBytes (1024).

capacity defaults to quickPlay.capacity, which defaults to size.max. The player count is read from playerCount on every heartbeat, defaulting to the Players service.

QuickPlay.closeAll(self: any) → ()

Delists everything this server is hosting.

Called from Matchmaker:stop, so a match server bound to game:BindToClose stops taking players the moment it starts shutting down rather than after listingExpiration. A server that dies without this is cleaned up by expiry anyway; this only makes it immediate.
