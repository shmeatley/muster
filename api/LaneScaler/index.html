LaneScaler

Decides how many lanes a partition should have, and moves it there safely.

The shared record

One MemoryStore entry per partition holds { count, previous, changedAt }. Every server reads it (cached for LANE_STATE_REFRESH seconds) to know where to write tickets, and any worker may propose a change through a compare-and-set. There is no coordinator.

Why resizing is safe

The count is stamped into every lane key, so servers that disagree about it write to different key spaces rather than corrupting one. A ticket is always readable in the lane its writer put it in — the writer keeps scanning that lane for as long as the ticket lives, and workers on the new count also read the old maps through Lanes.legacyMaps. Nothing is stranded, and the two pools see each other throughout.

The cooldown between changes is a full ticketExpiration. That is deliberate: it guarantees every ticket written under an abandoned count has expired or matched before that count can come back into use, so a lane name is never reused while stale entries sit in it.

Counts the scaler chooses are always powers of two, because it only ever starts at one and doubles or halves. That is what makes Lanes.legacyMaps exact. A pinned count is under no such constraint — it never resizes, so it has no previous count to map from.

When it changes

Each worker judges only the lane it holds. Lanes are hashed uniformly, so one lane's depth times the count estimates the whole queue.

  • Grow (double) after LANE_SATURATED_PASSES consecutive scans that come back at the batch cap. A saturated lane means the worker is only seeing the oldest slice of it, which biases matching.
  • Shrink (halve) after LANE_STARVED_PASSES consecutive scans below LANE_STARVED_DEPTH, when the count is above 1. Over-sharding is the worse failure: it scatters a thin queue so nobody matches at all.

Both directions are gated on consecutive observations, so a single burst or lull does not move anything.
