LaneScaler

Chooses how many lanes a partition is divided into, and changes it at runtime.

Active when lanes is "auto", which is the default. A pinned count skips this entirely: no record is written and no resize occurs.

The shared record

One MemoryStore entry per partition holds { count, previous, changedAt }. Servers read it to decide where to write tickets, cached for LANE_STATE_REFRESH (30 s), and any worker may change it by compare-and-set. There is no coordinator. A missing or malformed record falls back to the last value this server saw, or to one lane.

Resize rules

  • Grow, doubling, after LANE_SATURATED_PASSES (3) consecutive scans that return a full batch. A saturated lane means the worker sees only its oldest slice.
  • Shrink, halving, after LANE_STARVED_PASSES (5) consecutive scans below LANE_STARVED_DEPTH (8) candidates, while the count is above one.
  • Changes are at least ticketExpiration apart.

Each worker judges only the lane it holds. Because lanes are hashed uniformly, one lane's depth multiplied by the count approximates the queue.

Counts are therefore always powers of two, starting from one, which is what makes Lanes.legacyMaps exact.

Why a resize does not lose tickets

The count is stamped into every lane key, so servers holding different counts read and write separate key spaces. A ticket stays in the lane its writer chose, and that writer keeps scanning the lane for as long as the ticket lives. Workers on the new count additionally read the old maps their lane draws from, so tickets written under either count can still match each other.

The cooldown exists so an abandoned count fully drains before it can be chosen again, which means a lane name is never reused while stale entries remain in it.
