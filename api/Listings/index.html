Listings

This item is only intended to be used by the module's authors. Private

Store layout and atomic operations for the Quick Play listing index.

The shape mirrors the ticket index exactly: a hash map holding the record, and a lane sorted map holding a small denormalized copy for discovery. Everything that changes occupancy goes through the hash map, because that is the only structure the Store contract can compare-and-set.

The sort key is free seats

Entries are sorted by seats free, ascending, so a range read returns the fullest joinable match first, which is what backfill wants: a 7/8 game is completed before a 2/8 one is grown. A listing with no seats left is removed from the index entirely rather than left in it with a zero, so a range read is never spent on matches nobody can join.

Why claiming needs no lock

Fifty lobby servers can see the same 7/8 match at once, and exactly one of them may take the last seat. claim is a single compare-and-set: the store re-runs the loser's transform against the winner's write, the seat is gone the second time around, and the loser moves on to its next candidate. There is no lease and no coordination, because the store is already a serialization point.

Reservations

A host reports its player count on a heartbeat, so between beats the count is stale by up to heartbeatInterval. A claim writes a reservation holding the seats until the players actually arrive, which is what stops two lobbies from both filling the same slot inside one heartbeat window.

A reservation retires in one of two ways, and both matter:

  • The host's next heartbeat reports every one of its userIds as present. They arrived, so they are already inside players and counting them again would under-fill the match for the rest of the reservation window.
  • It expires. That is the backstop for a player who took a seat and never arrived, because their teleport failed or their server died.
