Lanes

Key layout for the queue index.

A queue is split into partition values (whatever partitionKey returns, or "all"), and each partition into some number of lanes. A ticket is hashed into exactly one lane and is matched against the other tickets in it.

Lanes buy parallelism by splitting the pool. One lane means one worker sees every queued ticket and matches on its first scan; four lanes means four servers can match simultaneously, each seeing a quarter of the queue. That trade only pays once a single lane is deep enough to fill matches on its own — a two-player queue split across 64 lanes would leave its two players in different lanes, never matching.

Because the right number depends on live queue depth, LaneScaler adjusts it at runtime and the count is stamped into every key: 

mu1:ranked:idx:EMEA:n04:02
                     ^^^ ^^
                   count lane

That stamp is what makes changing the count safe. Two servers that disagree about the count are not fighting over one key space; they are reading and writing different ones, and every ticket stays exactly where its writer put it. Nothing is ever stranded by a resize — the worst case is that two pools briefly do not see each other, which legacyMaps closes.

Sort keys are queue timestamps, so an ascending range read is oldest-first and matching is fair by default.

legacyMaps​

</>
Lanes.legacyMaps(
settings: any,
partition: string,
count: number,
lane: number,
previous: number?
) → {string}

The maps from previous that could hold tickets whose lane, at count, is lane.

Only LaneScaler resizes, and it only ever doubles or halves from one, so both counts here are always powers of two. That is what makes this exact rather than approximate. A ticket hashes to h % count:

  • Growing (count > previous): a ticket in old map o satisfies h % previous == o, so its new lane is one of o, o + previous, o + 2*previous, … Reading old map lane % previous therefore covers it.
  • Shrinking (count < previous): h % count == (h % previous) % count, so every old map o with o % count == lane contributes.

Either way the result holds at most previous / count entries — one when growing, two on a single halving.
